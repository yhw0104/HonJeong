# 🍽️ 식당 데이터 전략 — 혼정

> 결정일 2026-06-19 · 이 문서는 `places`(식당) 데이터의 **출처·소유·식별자·로드맵**에 대한 단일 기준(source of truth)이다.
> 상세 설계: [`superpowers/specs/2026-06-19-place-public-data-master-design.md`](./superpowers/specs/2026-06-19-place-public-data-master-design.md)

## 1. 한 줄 요약

식당 마스터 데이터는 **공공데이터(전국일반음식점표준데이터)** 를 일괄 적재해 **우리 DB가 소유**한다. 카카오는 **지도 렌더링 SDK 전용**이다. 메뉴·편의시설은 **점주 직접 등록(P2)** 으로 채운다.

## 2. 왜 카카오가 아니라 공공데이터인가

| | 카카오 로컬 API | 공공데이터(인허가 표준) |
| --- | --- | --- |
| 데이터 저장 | ❌ **장기 저장 약관 위반**(운영정책 제20조 — 1~2h 캐싱만 허용, 위반 시 API 차단) | ✅ 이용허락 "제한 없음"(상업·저장 자유) |
| 커버리지 | 실시간 검색만 | 전국 약 213만 건 |
| 좌표 | WGS84 즉시 | EPSG:5174 → 변환 필요 |
| 갱신 | 실시간 | 매일(변경분 API) |
| 비용 | 무료(쿼터) | 무료 |

→ **실운영 + 데이터 소유**가 목표이므로, 저장이 허용되는 공공데이터를 마스터로 삼는다. 카카오 로컬 데이터를 DB에 쌓으면 운영 중 차단 위험.

근거(확인): 카카오 데브톡 공식 답변(devtalk.kakao.com/t/api/140197), 공공데이터포털 전국일반음식점표준데이터(data.go.kr/15096283, 이용허락 제한없음).

## 3. 식별자(identity) 원칙

- **`places.id`(surrogate)가 시스템의 식당 식별자.** 체크인·리뷰·메뉴·편의시설 등 모든 UGC가 이 id로 FK 연결.
- 외부 소스 키는 **참조 속성** `source_id`(공공데이터 관리번호)일 뿐. 카카오 id는 저장하지 않는다.
- 향후 다른 출처(관리자 직접입력 등)가 생기면 `source` enum으로 구분(`PUBLIC_DATA`/`MANUAL`/…). → 두 출처를 라이브로 섞지 않으므로 **entity resolution(매칭) 문제 없음**.

## 4. 데이터 2층 구조

```
[공공데이터]  →  places (마스터: 상호·주소·좌표·업태·영업상태)   ← 검색·주변·체크인의 기준
                      ↑ FK(place_id)
[점주등록/UGC/관리자]  →  place_menus · place_facilities (P2)      ← 메뉴·편의시설(어느 소스도 미제공)
```

- **마스터(공공데이터)**: 사용자가 처음부터 전국 식당을 발견·체크인할 수 있는 토대.
- **강화층(P2)**: 메뉴·편의시설은 카카오·공공 둘 다 안 주므로 자체 축적. 안전한 길은 **점주 직접 등록**(네이버 스마트플레이스 패턴) — 식당은 이미 마스터에 있고 점주가 "클레임" 후 채움. 크롤은 법적 리스크(여기어때↔야놀자 형사사건 등)라 신중.

## 5. 적재(로딩)는 앱 밖 ETL — 런타임과 분리

> **결정**: 데이터 로딩(초기 일괄 + 매일 동기화)은 **백엔드 앱 안에 두지 않는다.** 요청을 서빙하는 런타임(스키마·엔티티·검색/주변/체크인)만 앱에 있고, `places`를 **채우는 일은 외부 ETL**이 한다. 앱은 proj4j·opencsv·적재 코드 없이 가볍게 유지한다(2026-06-19 `places/ingest` 제거, commit c135641).

**경계선**
```
런타임(앱 필수)   : Flyway 마이그레이션(스키마) · Place 엔티티 · 검색/주변/체크인 로직
외부 ETL(앱 밖)   : 초기 전국 적재 + 매일 변경분 동기화 (DB의 places 테이블을 직접 채움)
```

### 외부 ETL 절차 (초기 적재)
1. **다운로드** — localdata.go.kr에서 전국일반음식점 **CSV**(약 213만, 인코딩 CP949). xlsx 금지(100만행 한계).
2. **좌표 변환** — `EPSG:5174`(Bessel 중부원점TM) → `WGS84(4326)`.
   - Python: `pyproj.Transformer.from_crs("EPSG:5174","EPSG:4326",always_xy=True)` (towgs84 datum shift 포함)
   - 또는 DB: PostGIS `ST_Transform(ST_SetSRID(ST_MakePoint(x,y),5174),4326)`
   - ⚠️ EPSG:**2097 아님 5174**. (참고 proj 정의: `+proj=tmerc +lat_0=38 +lon_0=127.0028902777778 +k=1 +x_0=200000 +y_0=500000 +ellps=bessel +units=m +no_defs +towgs84=-115.80,474.99,674.11,1.16,-2.31,-1.63,6.43`)
3. **필터** — `영업상태명`에 영업/정상 포함만, 좌표/관리번호 결측 행 skip.
4. **적재** — 스테이징 테이블 `\copy` 후 `INSERT INTO places(...) ... ON CONFLICT (source, source_id) DO UPDATE`(멱등). 빠른 대량적재는 `COPY` 기반.
   - 컬럼 매핑: 관리번호→`source_id`(+`source='PUBLIC_DATA'`), 사업장명→`name`, 위생업태명→`category`, 소재지/도로명주소, 소재지전화→`phone`, 영업상태→`business_status`(영업/폐업), 변환좌표→`latitude/longitude`.
5. **검증** — `SELECT count(*) FROM places;` + 알려진 식당 위경도를 지도에서 확인(좌표변환 검증).

### 외부 ETL 절차 (매일 동기화, P2)
- LOCALDATA 오픈API의 **변경분**(전일까지)을 받아 같은 `ON CONFLICT` upsert. cron(또는 별도 스케줄러)으로 앱 밖에서 실행. 폐업분은 `business_status` 갱신으로 숨김.

### 적재 현황 / 데이터셋 선택 (2026-06-19)
- **적재됨**: **일반음식점**(전국일반음식점표준데이터) → 영업 **655,161건** 적재 완료. 좌표 변환·검색·주변검색 실데이터 검증 OK.
- **보류**: **휴게음식점**(카페·분식·패스트푸드·제과 등). staging까지 적재해봤으나(영업 189,838건) **롤백**. 이유 ↓.
- **롤백 안전장치**: 휴게음식점은 `places_staging`(=`places` 구조 복제)에 먼저 적재→검증→승인 시에만 `places`로 promote하는 방식. `load_places.py --table places_staging`. 잘못되면 `DROP TABLE places_staging`만 하면 됨(`places` 무영향).

> ⚠️ **휴게음식점 큐레이션 문제(미해결, 재논의 예정)**: 휴게음식점 면허는 *혼밥/혼카페 식당*과 *벌툰(만화카페)·편의점·키즈카페·PC/스터디카페*를 **구분하지 못한다.** 동네 카페와 만화카페가 **같은 `위생업태명='기타 휴게음식점'`** 이라 카테고리로도, 이름 필터로도(양방향 오류) 신뢰 분리 불가. 즉 "혼밥 가능 여부"는 인허가 데이터에 없음 → **사용 신호(체크인)·점주 클레임·별도 큐레이션이 진짜 출처**. 다시 올릴 때 후보안: ⓐ `커피숍`(75K, 비교적 신뢰) 등 명확 업태만(116K) / ⓑ 전체(190K, 노이즈 감수) / ⓒ 점주·사용 기반 점진 노출. 현재는 ⓐ/보류 사이에서 결정 보류.

## 6. 로드맵

| 단계 | 내용 | 위치 |
| --- | --- | --- |
| **P1 (앱)** | `places` 마스터 스키마(V2~V4) + 우리 DB 검색/주변검색 + 체크인 `placeId` 전환 + 카카오 경로 제거 | 백엔드 앱 |
| **P1 (ETL)** | 공공데이터 전국 1회 적재(CSV→좌표변환→upsert) | **앱 밖 스크립트** |
| **P2** | 매일 변경분 동기화 · 결측 좌표 지오코딩(도로명주소/VWorld) · 식당 상세 EP(`GET /api/places/{placeId}`) · **점주 등록/클레임** · 메뉴·편의시설 | ETL(동기화)/앱(상세·점주) |
