```
          ┌───────────────────┬─────────────────────┼─────────────────────┬─────────────────────┐
          │                   │                     │                     │                     │
          ▼                   ▼                     ▼                     ▼                     ▼
┌──────────────────┐  ┌────────────────────┐  ┌──────────────────┐  ┌────────────────────┐
│  PostgreSQL DB   │  │ 카카오 로컬 API    │  │ Push 알림(선택)  │  │ 파일 스토리지(추후) │
│  (users,places,  │  │ (장소 검색)        │  │ Expo Push / FCM  │  │  S3 등 (사진/2단계) │
│   check_ins,     │  │  external          │  │  (NFR-08)        │  └────────────────────┘
│   meal_requests) │  └────────────────────┘  └──────────────────┘
└──────────────────┘
```

- **앱(RN)**: UI·지도 렌더링·위치 권한. 서버에서 받은 데이터로 화면 구성.
- **백엔드(Spring)**: 인증, 비즈니스 로직, 집계, 외부 API 프록시·캐싱.
- **DB(PostgreSQL)**: 사용자·체크인·반응·같이먹기 신청(meal_requests) 등 UGC 영구 저장.
- **카카오 로컬 API**: 가게 메타데이터 검색. 결과를 `places`에 캐싱.
- **알림(NFR-08)**: 같이먹기 신청 수신 알림. **폴링**이면 추가 인프라 없음 / **푸시**면 Expo Push 또는 FCM 연동. 방식은 설계 단계 확정.

## 2. 백엔드 계층형 아키텍처

```
요청 흐름:  Client → Controller → Service → Repository → DB
                         │           │
                         │           └─ 외부 API 호출 (PlaceApiClient → 카카오)
                         └─ DTO 변환 (Request/Response DTO ↔ Entity)
```

| 계층 | 책임 | 예 |
| --- | --- | --- |
| **Controller** | HTTP 요청/응답, 입력 검증(@Valid), DTO 매핑 | `CheckInController` |
| **Service** | 비즈니스 로직, 트랜잭션 경계(@Transactional) | `CheckInService` |
| **Repository** | DB 접근 (Spring Data JPA) | `CheckInRepository` |
| **Entity(domain)** | DB 테이블 매핑 객체 | `CheckIn`, `User` |
| **DTO** | 계층 간 데이터 전달 (요청/응답 분리) | `CheckInRequest`, `CheckInResponse` |
| **Client** | 외부 API 호출 캡슐화 | `KakaoPlaceClient` |
| **Config / Security** | 설정·필터·JWT | `SecurityConfig`, `JwtAuthFilter` |
| **Exception** | 전역 예외 처리(@RestControllerAdvice) | `GlobalExceptionHandler` |

원칙: **Controller는 얇게, 로직은 Service에**, Entity는 외부에 직접 노출하지 않고 DTO로 변환.

## 3. 백엔드 패키지 구조 (도메인형 — 권장)

> 계층형(controller/service/...로 최상위 분리)보다 **도메인형**이 기능 추가(레벨·미션 등) 시 응집도가 높아 권장.

```
com.honjeong
├── HonjeongApiApplication.java
├── global
│   ├── config        (SecurityConfig, WebConfig, ...)
│   ├── security      (JwtProvider, JwtAuthFilter, ...)
│   ├── exception     (GlobalExceptionHandler, ErrorCode, BusinessException)
│   └── common        (BaseTimeEntity, ApiResponse, ...)
├── auth
│   ├── controller / service / dto
├── user
│   ├── controller / service / repository / domain(User) / dto
├── place
│   ├── controller / service / repository / domain(Place)
│   ├── client (KakaoPlaceClient) / dto
├── checkin
│   ├── controller / service / repository / domain(CheckIn) / dto
├── reaction
│   ├── controller / service / repository / domain(Reaction) / dto
└── meal        (같이먹기 FR-108)
    ├── controller / service / repository / domain(MealRequest) / dto
```

> FR-107(혼밥러 목록 조회)은 별도 패키지 없이 **checkin 도메인의 조회**(place별 active 체크인)로 처리한다.

## 6. 목표 배포 아키텍처 (배포 단계 청사진)

> 지금 구현하지 않지만 설계 단계에서 방향을 못 박아 둔다.

```
GitHub Repo ──push──▶ GitHub Actions (CI/CD)
                          │ 1) build & test (gradle)
                          │ 2) docker build & push (이미지 레지스트리)
                          ▼
                  Cloud (단일 VM 또는 관리형 컨테이너)
                  ┌────────────────────────────────────┐
                  │ docker compose                      │
                  │  ├─ app (Spring Boot 컨테이너)       │
                  │  └─ db  (PostgreSQL 컨테이너/관리형) │
                  └────────────────────────────────────┘
```

- **컨테이너화**: `Dockerfile`(멀티스테이지 빌드), 로컬은 `docker-compose`(app+db).
- **CI/CD**: GitHub Actions — 빌드·테스트 → 이미지 빌드·푸시 → 배포.
- **클라우드(예시)**: 초기엔 단일 VM(예: 오라클 클라우드 무료 티어/EC2) + docker compose. 트래픽 증가 시 관리형(ECS/Cloud Run) 전환.
- **시크릿 관리**: API 키·DB 비밀번호는 환경변수/시크릿 매니저로 분리 (NFR-02).
