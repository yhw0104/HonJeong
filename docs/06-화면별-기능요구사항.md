# 📑 화면별 백엔드 기능 요구사항 — 혼정 (혼밥을 정상화하다)

> **목적**: 완성된 22개 앱 목업(`app/src/features/**`)을 분석하여, 각 화면이 동작하기 위해 **백엔드에서 제공해야 할 기능**을 화면별로 정리한 개발용 요구사항 문서.
> **입력**: `01~05` 설계 문서 + 목업 + 사용자 지시(카카오맵 / OAuth / 휴대폰 인증).
> **성격**: 기존 `05-API명세서`(MVP)를 **확장**한다. 여기서 제안하는 신규 엔드포인트/엔티티는 개발 단계에서 확정·정식 명세화 대상이다.

### 0.2 docs 대비 바뀐 핵심 전제 (⚠️ 의사결정 반영됨)
1. **인증 방식 변경**: `02/05` 문서의 MVP는 **이메일/비밀번호**였으나, 사용자 지시에 따라 **소셜 로그인(OAuth: 카카오·애플) + 휴대폰 번호 인증(SMS)** 으로 대체한다. → 이메일/비번 `signup/login`은 폐기 또는 보조로만(아래 §1.1).
2. **지도 = 카카오맵 SDK(렌더링 전용) · 식당 데이터 = 공공데이터 마스터**: 지도 렌더링만 카카오맵 SDK(RN). **장소 검색·좌표·주변은 서버가 공공데이터(전국일반음식점표준데이터, 약 213만 건) 일괄 적재 마스터(우리 DB)로 제공**한다. 카카오 로컬 API 데이터는 약관(운영정책 제20조)상 장기 저장 불가라 식당 데이터 출처로 쓰지 않는다. 동네(위치) 설정 역지오코딩은 공공(도로명주소 API/VWorld). (전략: [07-식당데이터-전략](./07-식당데이터-전략.md))
3. **MVP 범위 초과**: 목업은 즐겨찾기·메이트·리뷰·혼밥일기·챌린지/뱃지·알림설정·공지·차단신고·고객센터 등 `02` 문서의 P2/P3 또는 신규 기능을 포함한다. 본 문서가 이를 화면 단위로 흡수한다.

### 1.6 혼밥 상태(체크인) — 전역 ✅
- **혼밥중 토글**이 서비스 데이터의 시작점(FR-101). MapHome·RestaurantDetail 어디서 켜도 동일한 **단일 활성 체크인 1개**만 유지 — `POST /api/check-ins` 시 기존 ACTIVE 존재하면 `409`(05 §5 정책).
- **전역 '혼밥 중' 상태 바**(`HonbabStatusBar`): 토글 ON 동안 앱 어느 화면에서나 상단에 표시, '끝내기'로 종료. 화면 이동·앱 재진입 시 `GET /api/check-ins/me`로 상태 복원.
- 종료는 `PATCH /api/check-ins/{id}/end`. — 시작/종료/내상태 모두 `05 §5`에 명세 존재(**신규 엔드포인트 불필요**).

## 5. 우선순위 로드맵 (개발 순서 제안)

**P1 — MVP 동작 (인증 + 핵심 루프)**
1. 인증: OAuth(카카오/애플) + 휴대폰 인증 + 프로필 셋업(FR-004/005/006/003E) + 파일 업로드
2. 장소: 카카오 검색·주변·역지오코딩 + 식당 기본정보
3. 체크인: 시작/종료/내상태/통계/지도/같은식당목록 (✅ 대부분 명세 존재) — **G1 해소: 혼밥 시작/종료 토글 + 전역 상태 바 구현(신규 EP 불필요)**
4. 같이먹기(신청+인사말/수락/거절) + 받은신청 *(반응 FR-106은 보류)*
5. 프로필 조회/수정(More/MyProfile/ProfileEdit)

**P2 — 경험 강화**
- 즐겨찾기 그룹 · 메이트(추가/프로필) · 리뷰=혼밥일기 통합+친화도 · 활동기록/통계 · 뱃지 · 알림설정 · 차단/신고 · 푸시 발송

**P3 — 콘텐츠/운영**
- 챌린지/미션 · 메이트 추천 · 공지사항 · 고객센터(FAQ/문의) · 식당 추천(FR-302)

## 6. 개발 착수 전 확정 필요 의사결정
0. ✅ **장소 데이터 출처** — **결정됨(2026-06-19)**: 카카오 로컬 데이터는 약관(운영정책 제20조)상 장기 저장 불가 → **공공데이터(전국일반음식점표준데이터, 약 213만 건)를 일괄 적재한 우리 DB 마스터**로 확정. 카카오는 **지도 렌더링 SDK 전용**. 검색·주변·체크인은 우리 `places.id` 기준(좌표 EPSG:5174→WGS84 변환). 동기화·결측 지오코딩·식당상세 EP는 P2. (스펙: `docs/superpowers/specs/2026-06-19-place-public-data-master-design.md`, [07-식당데이터-전략](./07-식당데이터-전략.md))
1. ✅ **인증** — **결정됨**: 이메일/비번 **완전 폐기**, OAuth(카카오/애플)+휴대폰 인증으로 대체. (G·§1.1, 05 §2 반영)
2. ✅ **체크인 진입점**(G1) — **결정됨**: 두 위치 모두 채택 — MapHome(혼밥 시작 → 장소 선택 시트 → 토글) + RestaurantDetail(해당 식당 직접 토글) + 전역 '혼밥 중' 상태 바. **남은 확정**: 종료 트리거 정책 — 수동 '끝내기'만 vs 시간 만료/위치 이탈 시 자동 종료.
3. ✅ **식당 상세 데이터 출처**(G3/§4.7) — **방향확정**: 메뉴·편의시설은 카카오·공공 둘 다 미제공 → **점주 직접 등록(가장 안전, P2)** 우선 + 관리자/UGC 보조(크롤은 법적 리스크). 사진=`review_photos` 집계. 공공 마스터가 부착 토대.
4. ✅ **리뷰 ↔ 혼밥일기 통합**(G4) — **결정됨**: `reviews` 하나로 **통합**(별점·사진·친화태그 공유, 좋아요/댓글 없음, 다회 작성).
5. **혼밥 친화도 산식**: `reviews.solo_friendly_rating` 평균 + `review_tags` 빈도 집계 공식 정의.
6. **알림 방식**(NFR-08): 푸시(Expo/FCM) vs 폴링 — P1 같이먹기 알림부터.
7. **SMS/OAuth 공급자·키 관리**: SMS(NCP SENS/Twilio/Firebase), 애플 로그인(서버 검증), 비용·시크릿(NFR-02).
8. **메이트 vs 같이먹기 관계 정책**(G5): 메이트 신청/수락 플로우, 차단과의 상호작용.
